# RideIQ Architecture Decision Record (ADR)

**Status:** Accepted  
**Date:** 2026-11-23  
**Author:** RideIQ Architecture Team

---

## 1. Common Domain Boundary (Q1)

The four operational problems share a common boundary: **the ride-hailing trip assignment lifecycle**. Every domain operates on the same entities — drivers, riders, trips, zones — and observes the same lifecycle events (request, accept, start, complete, cancel, deviate). The shared boundary is the **trip context** combined with **time** and **geography**. Domain-specific risk definitions, models, permissions, and explanations remain isolated; only the underlying entities and event stream are shared.

## 2. Shared Core Services (Q2)

The following capabilities belong in shared core and are injected into domain services:

- Configuration manager
- Authentication & JWT validation
- Authorization (RBAC) engine
- Input/output validation (Zod)
- Database connection & transaction manager (Prisma)
- Cache abstraction (Redis optional)
- Structured JSON logging (Pino)
- Structured error handler
- Audit trail service
- Rate limiter
- External API adapter layer (typed HTTP clients)
- Model inference abstraction
- Event processing interface & transactional outbox
- Idempotency manager
- Approval workflow service
- PII masking & privacy utilities
- Decision receipt service

Domain services receive only the dependencies they need via constructor injection.

## 3. Domain-Isolated Logic (Q3)

The following remain isolated by domain:

- **Risk labels and definitions:** cancellation probability ≠ safety risk ≠ churn probability. Never combined into a universal score.
- **Models:** each domain maintains its own model version and feature set.
- **Permissions:** each tool/resource has a domain-specific required role.
- **Explanations:** domain-specific evidence and alternative explanations.
- **Data purpose:** safety data is never used for retention decisions; reliability data is never used for safety scoring.

## 4. MCP Tool Classification (Q4)

| Classification | Examples |
|---|---|
| Read-only | `driver_get_reliability`, `safety_get_live_deviation`, `matching_get_zone_metrics`, `retention_get_driver_feedback` |
| Computational | `driver_predict_cancellation_risk`, `safety_evaluate_deviation`, `matching_calculate_score`, `retention_query_churn_risk` |
| Proposal-only | `matching_update_production_weights` (default dry-run), `retention_send_incentive` (requires approval) |
| State-changing | `driver_reassign_trip`, `safety_trigger_emergency_protocol`, `safety_escalate_incident`, `retention_send_incentive` (after approval) |

All state-changing tools require server-side authorization + idempotency + audit logging.

## 5. Cross-Module Intelligence (Q5)

The Unified Intelligence Layer:

- Requests minimum required domain data through domain service interfaces.
- Applies authorization and purpose restriction before every data access.
- Preserves domain-specific model labels, risk definitions, and evaluation criteria.
- Never converts a reliability prediction into a safety score; never uses safety data for retention.
- Returns evidence references, timestamps, data quality, uncertainty, and permitted uses.
- Distinguishes possible common causes from confirmed causes.

## 6. Evidence Provenance (Q6)

Every signal is labeled with one of:

- **OBSERVED:** retrieved from an operational source.
- **CALCULATED:** mathematically derived from observed data.
- **PREDICTED:** estimated by a model.
- **SIMULATED:** generated by the digital twin / scenario engine.
- **INFERRED:** plausible interpretation not established as fact.

Decision traces store references to source records, never copying unnecessary personal information.

## 7. Uncertainty & Evidence Communication (Q7)

- Probability is never equated with confidence.
- Evidence quality: high / medium / low / insufficient.
- Data freshness and sample size returned with every prediction.
- `INSUFFICIENT_EVIDENCE` state returned when data doesn't support a conclusion.
- No fabricated confidence percentages.

## 8. Fairness & Anti-Discrimination (Q8)

- No protected personal characteristics used for ranking, scoring, or incentive allocation.
- Fairness metrics normalized against eligible exposure (denominators explained).
- No assumption that every driver should receive identical trips/earnings.
- Opportunity exclusion detected but not assumed to be discriminatory without evidence.

## 9. Emergency Workflow Safety (Q9)

- Route deviation alone is not evidence of danger.
- Human authorization mandatory by default for escalation.
- Narrowly defined emergency exceptions must be configured, legally reviewed, documented, and tested.
- Idempotency keys prevent duplicate escalation.
- Synthetic demonstrations simulate emergency actions only; never contact real authorities.

## 10. No Real Data / Untrained Models (Q10)

- All demonstration data explicitly labeled **SYNTHETIC**.
- Transparent TypeScript baseline models; never presented as production-grade AI.
- Optional Python model service behind a typed interface; server works without it.
- Synthetic scenario metrics validate software behavior, not real-world accuracy.

## 11. Digital Twin Shared State (Q11)

- Single shared marketplace state model.
- Deterministic discrete-event simulation with configurable random seeds.
- Same seed + same inputs + same version = same outputs.
- All four domains operate against the same simulation snapshot and timeline.
- Clearly labeled **SIMULATED RESULT — NOT A REAL-WORLD PERFORMANCE CLAIM.**

## 12. Scalability (Q12)

- One MCP server, not microservices.
- STDIO + Streamable HTTP transports.
- Stateless Streamable HTTP; no legacy session assumptions.
- Event worker and optional model adapter run as separate processes from same repo.
- Horizontal scalability via stateless HTTP + shared database, not premature complexity.

## 13. Differentiation (Q13)

RideIQ differs from four separate MCP servers through:

- **Shared infrastructure:** one auth, one audit, one database, one decision trace.
- **Cross-module intelligence:** correlates evidence across domains without bypassing permissions.
- **Digital Twin:** all four domains simulate against one shared marketplace state.
- **Unified briefing:** one consolidated view across reliability, safety, fairness, and retention.
- **Single decision receipt:** auditable trail spanning all domains.

## Technology Choices

| Choice | Justification |
|---|---|
| TypeScript + Node.js | Official MCP SDK is TypeScript-first; single language for server and tools |
| `@modelcontextprotocol/server` v2 + `@modelcontextprotocol/node` | Official stable TypeScript SDK v2 package split; implements the 2026-07-28 MCP spec and provides the Streamable HTTP Node adapter |
| Zod | Standard Schema-compatible validation; official MCP SDK integration |
| PostgreSQL + Prisma | Relational integrity for audit/approval/idempotency; Prisma offers excellent TypeScript support |
| Pino | Structured JSON logging for production observability |
| Redis (optional) | Caching and rate limiting; graceful degradation when unavailable |
| Vitest | Fast, native ESM test runner |
| Docker + Docker Compose | Reproducible development and deployment |

## Transport Support

- **STDIO:** For local MCP clients (Claude Desktop, Cursor, VS Code). Stdout reserved for MCP protocol; logs to stderr.
- **Streamable HTTP:** For remote deployments. Stateless request model per SDK. Localhost by default in development.

## Decision Receipt Contract

Persisted privacy-minimized record per decision with:
- Decision ID, timestamp, category, source module
- Pseudonymous entity references
- Data source references and freshness
- Model/policy/config versions
- Observed/calculated/predicted/simulated/inferred signals
- Contributing factors, uncertainty, alternative explanations
- Recommendation and required approval state
- Human decision and final outcome
